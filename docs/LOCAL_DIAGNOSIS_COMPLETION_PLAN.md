# 바로미 로컬 진단 완주 계획

## 이번 목표

배포와 AI 분석은 다루지 않는다. 사용자가 로컬 화면에서 URL과 테스트 계정을 입력하고 진단을 시작하면, 서비스의 핵심인 **쇼핑몰 전체 크롤링과 다크패턴 진단**이 실제로 동작해야 한다. 시작 URL만 확인하거나 구매 흐름 몇 화면만 방문한 결과를 전체 진단으로 취급하지 않는다. 사이트맵, 내부 내비게이션, 카테고리·검색·페이지네이션 등에서 발견되는 같은 쇼핑몰의 안전한 페이지를 큐가 빌 때까지 순회하고, 각 페이지의 증거를 16개 진단 유형과 연결한다. 구매 흐름 및 별도 탐색 영역도 함께 확인한다. 작업은 성공·부분 완료·실패 중 하나로 반드시 종료하며, 실제 크롤링 범위, 방문·실패·차단·미방문 경로, 16개 유형별 결과·근거·미검사 사유가 담긴 보고서를 열고 내려받을 수 있게 한다.

`VERO LIVING`, `MEGA SALE` 및 아래 `Set A` 7개 사이트는 회귀 검증 대상이다. 판정 규칙을 특정 URL·상점명·문구에 맞춰 하드코딩하지 않고, 표면과 구조가 다른 사이트에서도 같은 의미 기반 탐색 규칙을 사용한다. 계정 비밀번호와 인증정보는 이 문서와 코드에 저장하지 않는다.

| 사이트 | 기대 위반 수 | 필수 유형 |
|---|---:|---|
| VERO LIVING | 0 | 위험 판정 없음. 상품가=최종 금액, 미리 체크된 유료 옵션 없음, 원클릭 취소를 음성 대조 근거로 확인 |
| MEGA SALE | 4 | `PRESELECTION`, `HIDDEN_SUBSCRIPTION`, `URGENCY_SCARCITY`, 로그아웃 버튼 은닉은 `HIDDEN_INFO` 또는 `MISDIRECTED_HIERARCHY` 검토 신호로 한 건만 분류 |

## 필수 외부 검증 집합: Set A

각 사이트에서 PC 기준으로 진단을 시작해 전체 크롤링·terminal 상태·최종 보고서까지 확인한다. 보고서의 확정/검토 분류와 근거는 정답 유형과 대조한다. 상품 한 화면만 보고 끝내거나 보고서 전 단계에서 통과 처리하지 않는다. VERO와 PURE CRAFT는 서로 다른 구조의 클린 음성 대조군이다.

| 사이트 | 기대 위반 수 | 필수 유형 |
|---|---:|---|
| PURE CRAFT | 0 | 위험 판정 없음 |
| LUMEN BEAUTY | 1 | `URGENCY_SCARCITY` |
| FIT VORTEX | 2 | `PRESELECTION`, `CONFIRM_SHAMING` |
| CHRONO VINTAGE | 3 | `FALSE_DISCOUNT`, `DRIP_PRICING`, `PRESELECTION` |
| PET BLISS | 4 | `URGENCY_SCARCITY`, `DRIP_PRICING`, `HIDDEN_SUBSCRIPTION`, `CANCELLATION_OBSTRUCTION` |
| WANDER PASS | 5 | `DRIP_PRICING`, `PRESELECTION`, `HIDDEN_SUBSCRIPTION`, `CONFIRM_SHAMING`, `CANCELLATION_OBSTRUCTION` |
| NEXUS STREAM | 6 | `URGENCY_SCARCITY`, `DRIP_PRICING`, `PRESELECTION`, `HIDDEN_SUBSCRIPTION`, `CONFIRM_SHAMING`, `CANCELLATION_OBSTRUCTION` |

정답의 구체 근거(옵션 체크 상태와 금액 변화, 최초·최종 가격, 타이머/긴박 문구, 자동 갱신 고지, 거절 문구, 취소 경로 단계)는 화면 증거와 보고서에서 추적 가능해야 한다. `PURE CRAFT`는 음성 대조군으로 사용하며 실제로 검사한 범위에서 위험을 만들어내지 않아야 한다. 이 집합의 전 사이트가 보고서까지 도달하기 전에는 “전체 크롤링 및 분류가 검증됐다”고 말하지 않는다.

## 이번 목표에서 제외

- 유료 AI 정밀 분석, 파인튜닝, DL 분류기
- 운영 배포, 조직 권한, Supabase/Vercel 설정
- 최종 시각 디자인
- 모든 사이트에서 모든 유형을 강제로 판정하는 것

증거가 부족한 유형은 정상 결과인 것처럼 표시하지 않고 `NOT_TESTED`와 구체적인 사유를 남긴다.

## 관찰 사실과 의미 판단의 경계

크롤러는 화면에 실제로 있는 문구·요소·상태·금액·경로를 수집한다. 요소가 존재한다는 사실만으로 다크패턴이라고 판정하지 않는다.

- **기본 엔진이 확인할 사실:** 체크박스의 초기 선택 상태, 단계 전후 금액 차이, 페이지와 링크의 실제 도달 여부, 가입·해지 경로의 단계 수, 화면에 표시된 타이머·재고·추천·광고 문구, 요소의 크기·색상·위치
- **의미 해석이 필요한 후보:** 타이머가 소비자를 압박하는 긴박감인지, 재고·조회 수치가 허위인지, 추천이 기만적인지, 거절 문구가 죄책감을 유도하는지, 시각적 차이가 중요한 대안을 가리는지
- **이번 목표에서의 처리:** 의미 해석이 필요한 후보는 원본 증거와 함께 `REVIEW_NEEDED`로 보고한다. 이번 로컬 완주 목표에서는 AI를 호출하지 않으며, 기본 엔진의 사실 증거와 검토 후보를 분리해 보존한다. 선택형 AI 분석은 기본 보고서가 끝난 다음 별도 범위로 구현한다.

예를 들어 타이머 문구가 보이면 크롤러는 문구와 화면 증거를 저장한다. 그 문구가 실제로 허위 긴박감을 만드는지 확인하지 못했다면 확정 위반으로 표시하지 않는다.

## 절대 완료 조건

다음 조건을 모두 만족하기 전에는 이번 목표를 완료했다고 말하지 않는다.

1. 진단 생성부터 보고서 열람까지 브라우저 E2E가 통과한다.
2. 진행 화면에서 구매 흐름 3단계와 별도 탐색 7영역의 현재 상태가 실제 작업과 함께 갱신된다.
3. 작업은 `COMPLETED`, `PARTIAL`, `FAILED`, `CANCELLED` 중 하나로 끝나며 무한 로딩 상태가 없다.
4. 완료한 단계, 경로 미발견, 접근 차단, 작업 실패를 서로 다른 상태와 사유로 기록한다.
5. 보고서에는 16개 유형이 모두 있고 각 유형은 `SUSPECTED`, `REVIEW_NEEDED`, `NOT_OBSERVED`, `NOT_TESTED` 중 하나다.
6. `NOT_OBSERVED`는 해당 유형에 필요한 증거를 실제로 검사한 경우에만 사용한다.
7. 보고서 JSON과 화면에서 증거 ID, 미검사 사유, 단계별 소요 시간이 확인된다.
8. 보고서 다운로드가 동작한다.
9. VERO와 MEGA의 PC 경로가 각각 3회 연속 보고서까지 도달한다.
10. 로컬 fixture의 장바구니 경유·바로구매·로그인 필요·경로 없음·접근 실패 시나리오가 모두 통과한다.
11. 정상 소형 쇼핑몰 회귀 실행은 목표 30초 이내이며, 초과 시 전체 타임아웃을 늘리지 않고 가장 느린 단계의 원인을 기록해 개선한다.
12. `npm run typecheck`, 탐지 단위 테스트, 웹 E2E가 통과한다.
13. 전체 크롤러가 사이트맵과 내부 내비게이션에서 발견한 같은 쇼핑몰의 안전한 페이지 큐를 소진한다. 방문·실패·차단·미방문 URL과 페이지별 증거를 보고서에 남긴다. 큐가 남거나 페이지 접근이 실패하면 전체 진단은 완료로 표시하지 않는다.
14. 기준몰 2개와 `Set A` 일곱 사이트 모두에서 전체 크롤링과 보고서가 끝까지 생성되고, 두 clean 0건과 위험 사이트의 유형·근거를 정답 집합과 대조한다.

## 상태 계약

### 작업 상태

- `QUEUED`: 아직 워커가 시작하지 않음
- `RUNNING`: 적어도 한 단계가 실행 중
- `COMPLETED`: 필수 실행 파이프라인이 종료되고 보고서가 생성됨
- `PARTIAL`: 보고서는 생성됐지만 하나 이상의 필수 단계가 차단·미발견·실패
- `FAILED`: 보고서를 만들 최소 증거도 수집하지 못함
- `CANCELLED`: 사용자 취소가 반영됨

### 단계 상태

구매 단계 3개와 별도 탐색 영역 7개에 동일한 상태 모델을 사용한다.

- `PENDING`, `RUNNING`, `COVERED`, `DISCOVERED`, `NOT_FOUND`, `BLOCKED`, `FAILED`, `SKIPPED`

각 단계는 `startedAt`, `finishedAt`, `durationMs`, `reason`, `evidenceIds`를 가진다. 단순한 전역 `currentStage`와 숫자 진행률만으로 진단 상태를 추측하지 않는다.

## 구현 순서

### 0. 현재 변경 보호와 기준선 고정

- 현재 dirty diff를 삭제하거나 되돌리지 않는다.
- 타입 검사와 기존 단위 테스트 결과를 기록한다.
- 현재 VERO/MEGA 실행 결과가 있다면 시간·단계·실패 사유를 기준선 JSON으로 보존한다.
- 새 기능을 넣기 전에 실패를 재현하는 테스트를 먼저 추가한다.

통과 기준: 기존 변경을 보존한 상태에서 타입 검사가 통과하고, 어떤 테스트가 실패하는지 목록이 남는다.

### 1. 진단 상태 머신과 실시간 진행 표시

- 구매 3단계와 별도 7영역을 하나의 `phaseResults` 계약으로 만든다.
- 워커가 단계 시작/종료 때마다 상태와 시간을 저장한다.
- API는 저장된 실제 상태만 반환한다. UI에서 임의로 완료나 미검사를 추정하지 않는다.
- 진행 화면은 10개 영역을 모두 표시하고 현재 실행 중인 영역을 명확히 보여준다.
- 워커 예외, 프로세스 재시작, 취소, 제한 시간 도달 시 반드시 terminal 상태로 닫는다.

통과 기준: 느리게 동작하는 fixture에서 상태가 `PENDING → RUNNING → terminal` 순서로 보이고 새로고침 후에도 동일하다.

### 2. 보고서 완주 경로 고정

- 성공뿐 아니라 부분 완료에서도 보고서 레코드를 먼저 만든 뒤 terminal 상태를 저장한다.
- 스냅샷, 표면 관찰, 가격 원장, 차단 사유로 16개 `ruleCoverage`를 항상 생성한다.
- 보고서 조회·화면 렌더·JSON 다운로드가 같은 데이터를 사용하도록 단일 응답 계약으로 고정한다.
- 보고서 생성 실패는 원인을 저장하고 진행 화면에서 재시도 가능한 실패로 표시한다.

통과 기준: 구매 흐름 일부가 실패하는 fixture에서도 `PARTIAL` 보고서가 열리고 16개 상태와 이유가 보인다.

### 3. 별도 탐색 7영역의 실제 증거 수집

구매 흐름 몇 단계만 검사하는 것으로 전체 사이트 진단을 대체하지 않는다. 별도 표면 탐색 전에 안전한 전체 페이지 크롤링이 실제로 동작해야 한다.

### 3a. 같은 쇼핑몰 전체 페이지 크롤링

- 시작 URL에서 발견한 같은 출처의 내부 링크를 큐에 넣고, 큐가 빌 때까지 페이지를 방문한다.
- 페이지별 canonical URL, HTTP 결과, 발견 출처, 깊이, 연결 수, 제목, 검사 가능한 본문 증거를 저장한다.
- 카테고리·검색 결과·상품·후기·정책·쿠폰·계정 안내 등 링크된 페이지를 순회한다. 페이지네이션과 필터 링크도 정규화해 방문 중복과 무한 루프를 방지한다.
- 결제 승인, 주문 확정, 장바구니 상태 변경, 로그인 제출, 쿠폰 적용, 구독 신청·해지, 탈퇴, 환불 요청 등 상태를 바꾸는 링크나 동작은 실행하지 않는다. 이런 경로는 발견만 기록하고 미검사 이유를 남긴다.
- 외부 출처로 이동하지 않고, 로그인된 테스트 계정의 동일 출처 세션만 재사용한다.
- 시간·페이지 안전 한도에 도달하면 남은 큐와 사유를 보고서에 보존하고 `PARTIAL`로 끝낸다. 임의의 페이지 수 제한으로 큐를 조용히 버리지 않는다.

통과 기준: 다중 카테고리·페이지네이션·반복 링크·외부 링크·상태 변경 링크를 포함한 fixture에서 모든 안전 내부 URL은 한 번씩 방문하고, 위험 동작은 실행하지 않으며, 미방문 큐가 남으면 완료로 표시하지 않는다.

한 번에 하나씩 구현하고 각 영역마다 성공·미발견·차단 fixture를 둔다.

1. `CATALOG`: 목록 가격, 품절/구매 가능 여부, 상세 가격과 대조
2. `AUTH`: 로그인·회원가입 요구 위치와 구매 필수 여부
3. `COUPON`: 쿠폰 조건, 만료, 자동 적용/해제 결과
4. `RECOMMENDATION`: 광고/추천/후기 표시 문구와 링크 관계
5. `SUBSCRIPTION`: 구독 가격, 갱신 주기, 기본 선택, 동의 문구
6. `CANCELLATION`: 해지·탈퇴·환불 경로 발견 여부와 단계 수
7. `POLICY`: 배송·교환·반품 조건 및 구매 화면과의 일관성

- 후보 링크 수와 클릭 수에 상한을 두고, 독립 영역은 가능한 범위에서 병렬로 읽는다.
- 상태 변화가 없으면 즉시 다음 후보로 넘어간다.
- 교차 출처·결제·주문 확정·계정 변경은 실행하지 않는다.

통과 기준: 각 영역이 최소 하나의 독립 fixture에서 `COVERED`가 되고, 없을 때는 `NOT_FOUND`, 접근 불가일 때는 `BLOCKED`가 된다.

### 4. 16개 유형의 증거 충족 조건 완성

각 유형마다 다음 네 항목을 코드와 테스트에 명시한다.

- 필요한 화면/상호작용 증거
- 자동 판정 가능한 사실 조건
- 사람 검토가 필요한 신호 조건
- 증거 부족 시 정확한 `NOT_TESTED` 이유

우선 남은 구조적 검사부터 구현한다.

1. `DISGUISED_AD`: 광고 표시와 콘텐츠/추천 카드의 관계
2. `CONFIRM_SHAMING`: 수락·거절 문구 쌍과 결과
3. `FORCED_ACTION`: 구매에 불필요한 가입·권한 요구
4. `MISDIRECTED_HIERARCHY`: 동일 결정군의 크기·대비·배치 차이
5. `CANCELLATION_OBSTRUCTION`: 가입 대비 해지 단계·접근성 차이
6. `FALSE_RECOMMENDATION`, `BAIT_SELLING`: 추천/후기 및 목록-상세 대조
7. 기존 9개 유형 회귀와 오탐 방지

문구만으로 위법 또는 확정 판정을 만들지 않는다. 실제 상태·금액·선택 결과가 있는 경우만 `SUSPECTED`, 의미 해석이 필요한 경우는 `REVIEW_NEEDED`다.

통과 기준: 16개 유형 각각 양성 1개, 음성 1개, 증거 부족 1개 테스트가 있으며 clean fixture에 위험 판정이 없다.

### 5. 성능 개선

- 전체 실행과 각 단계의 `durationMs`, 후보 수, 클릭 수, 네트워크 대기 시간을 기록한다.
- 고정 sleep을 상태 변화 대기로 교체한다.
- 목록 후보를 구조화 데이터·의미 있는 링크 순으로 축소한다.
- 독립적인 정적 표면 요청은 제한된 동시성으로 병렬화한다.
- 동일 URL/동일 DOM 증거는 중복 방문하지 않는다.
- 로그인은 한 번만 수행하고 같은 브라우저 컨텍스트를 재사용한다.
- 개별 단계 제한 시간과 전체 안전 제한 시간을 분리한다.

통과 기준: 성능 결과표에 p50/p95 대신 최소한 3회 실행의 각 시간과 최악 단계가 기록되고, VERO/MEGA 3회 연속 실행에서 무한 대기가 없다.

### 6. 최종 로컬 E2E 승인

사용자 관점으로만 검증한다.

1. 로컬 서버와 워커 시작
2. 진단 화면 접속
3. URL·계정 입력 및 동의
4. 진단 시작
5. 새로고침을 포함해 진행 상태 확인
6. terminal 상태 확인
7. 보고서 자동/수동 이동 확인
8. 16개 결과와 미검사 사유 확인
9. 보고서 다운로드 확인
10. VERO/MEGA 각각 3회 반복, Set A 7개 모두 1회 이상

최종 전달에는 성공 화면만 보여주지 않는다. 실행 ID, 총 시간, 단계별 상태, 16개 집계, 보고서 URL, 실패가 있었다면 그 이유를 함께 남긴다.

## 작업 단위와 커밋 경계

낮은 모델은 아래 한 줄만 한 번에 수행한다. 한 단위가 테스트를 통과하기 전 다음 단위로 넘어가지 않는다.

1. 상태 계약과 저장 구조
2. 워커 단계 이벤트와 terminal 보장
3. 진행 API/UI 반영
4. 부분 완료 보고서 보장
5. 별도 탐색 7영역
6. 미완성 유형의 구조적 검사
7. 계측과 성능 개선
8. 전체 로컬 E2E 및 회귀 수정

각 단위 종료 시 반드시 `변경 파일`, `통과한 테스트`, `실패한 테스트`, `실제 남은 일`을 기록한다. 실제 E2E 증거 없이 “완료”라고 쓰지 않는다.

중간 크기 이상의 구현 단위가 끝날 때마다 자동 테스트만으로 통과 처리하지 않는다. Headed 브라우저를 열어 진단 입력·진행 상태·최종 보고서를 실제로 확인하고, 화면에 표시된 상태가 저장된 진단 결과와 일치하는지 검증한 뒤 다음 구현 단위로 진행한다.

## 다음 모델이 지켜야 할 실행 규칙

- 현재 `backend` 브랜치와 dirty 변경을 그대로 이어간다.
- 서버 설정, 배포, AI 기능으로 범위를 넓히지 않는다.
- 사용자에게 진행률을 말할 때 코드 줄 수가 아니라 위 절대 완료 조건 12개 중 통과 개수를 사용한다.
- 오류를 타임아웃으로 숨기지 않는다. 먼저 가장 느린 단계와 대기 원인을 계측한다.
- 특정 테스트몰의 문구나 URL을 제품 코드에 하드코딩하지 않는다.
- 실패한 단계는 완료로 표시하지 않는다.
- 부분 완료는 보고서를 생성하되 미검사 이유를 숨기지 않는다.
- 테스트를 생략한 작업은 완료가 아니라 미검증이다.
- 사용자가 직접 보고서를 열어보기 전에는 최종 완료를 선언하지 않는다.


모델은 사용자가 직접 선택한다. 한 모델에서 작업을 시작하면 작업 도중 임의로 다른 모델을 선택했다고 가정하거나 전환을 선언하지 않는다.
